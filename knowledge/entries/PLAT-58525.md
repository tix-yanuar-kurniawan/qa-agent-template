# PLAT-58525 — Mission Order History
> **Related:** [[PLAT-58526]] · [[PLAT-58527]] · [[PLAT-58529]] · [[PLAT-58530]] · [[PLAT-58604]] · [[LoyaltyMissionSlugProgressGET]]

## PRD Summary

A new **Mission History** page listing the orders that contributed to a user's
mission progress, so the user can see *which order gave which stamp*, what it was
worth, and what state that contribution is in.

Reached two ways: the **History** button on the mission page, and **tapping a
stamp** on the stamp progress tracker (stamp missions only — a GBV mission has no
tracker, so the button is its only entry point).

Three mission types, served by one API:

| Type | Stamp contribution | Room nights |
|---|---|---|
| `ORDER_ID` (stamp per order) | shown | always `null` |
| `ROOM_NIGHT` (stamp per room night) | shown | Hotel/Homes only |
| `GBV` (progress bar by amount) | `null` | `null` |

Card anatomy (Figma, 360×800): status icon + stamp label on the same row as
`Order ID <id>` and a chevron; vertical icon + order name; then uppercase field
rows `TOTAL AMOUNT`, `ROOM NIGHTS` (conditional), `BOOKING DATE`, and a trip-date
row; then a note banner when the status is not `ACTIVE`.

Statuses and note copy (API doc — the authoritative table):

| status | level | stamp copy | GBV copy |
|---|---|---|---|
| `PENDING` | info | Stamps pending. You will get them once the trip is over. | Progress pending. You will get them once the trip is over. |
| `PROCESS_REFUND` | warning | Refund requested. You're no longer eligible to get stamps from this order. | Refund requested. You're no longer eligible to get progress from this order. |
| `PROCESS_RESCHEDULE` | warning | Reschedule requested. The number of stamps you'll get may change. | Reschedule requested. The number of progress you'll get may change. |
| `ACTIVE` | — | `note: null` | `note: null` |

`GET /tix-mission/api/mission/{slug}/order-history` — `limit` default 20 / max
100, cursor pagination via `nextCursor`, all amounts/dates/labels formatted
server-side from `Accept-Language`. Unenrolled → `400 USER_INELIGIBLE`, which is
what drives the enrollment bottom sheet. Unknown slug → `404 NOT_FOUND`.

## Figma Design Summary

The page has
four sections: **Flow**, **Wording**, **Responsive** (343 and 938 breakpoints),
and **Comms**. Three flows: *Pending Progress*, *Free Stamp*, *Haven't Join*.

- **The free-stamp flow settles the subtlest rule in the epic.** Its history
  screen shows a single card reading **`Stamp 2 to 3`** — the free stamp occupies
  Stamp 1, renders no card, and still consumes the number. That is the visual
  proof of the API flow's "calculate stamp sequence using `is_free_stamped =
  true`, then omit free stamps from items". A sticky note adds that free stamps are *set up from Admin* — no path
  given anywhere.
- **A sticky note contradicts the requirement it annotates.** The note against
  the Order ID chevron reads *"Directed to **Order Detail Page**"*, while the PRD
  and both FE stories specify `m.tiket.com/en-id/yourorder?utm_campaign=missionHistory`
  — the order **list**.
- **Refund and reschedule are drawn as actions on a *pending* order** ("User do
  action on pending order: Refund" / "Reschedule"), which matches the tiket order
  state machine: refund branches from issued/pending, never from finished.
- **Layer names carry a card state the API cannot produce**: `Card Isuued` [sic],
  `WIP Card`, `Refund Card`, and **`Waiting for Payment`**. No status value
  represents an unpaid order, and an unpaid order has no progress row.
- **The mock labels a TTD order's date row `STAY DATES`**, as does the PRD's
  per-vertical table, while the API doc says FE maps five labels from `vertical`.
  Design comment #279 is still asking for the non-hotel copy, so the label set is
  unsettled.
- Room nights read `2 (1 room x 2 night)` in the mock — **singular** — against
  `nights` in both the PRD and the API doc.
- The API doc's note table is newer than the design copy and is authoritative for
  exact strings.

## Key Learnings

- **The subtasks and the two Confluence pages are this epic's real scope; the
  Jira story bodies are the stale half.** Sorting, pagination, the empty state,
  the rail subtypes, and the entire second half of the refund rule appear
  *nowhere* in the epic or the four child stories. Reading only Jira would give
  behaviour that is now wrong.
- **Refund is two states and the Jira stories collapse them into one.** Every
  child story says only *"Refunded order: keep the order visible… show 'Refund
  requested…'"*. The PRD (v2, 08-13) and the API doc (v3, **08-20**) both split
  it: **refund *requested*** stays visible with the warning note and keeps its
  stamp label, while an **already-`REFUNDED`** order is *not returned at all*
  and the surviving orders re-sequence onto the freed numbers. This is the single
  most important reconciliation here.
- **Reschedule completion is genuinely contradicted, not just missing.** The PRD
  says remove the order and *show the newly rescheduled order ID*; the API doc
  says *the item returns as `PENDING`/`ACTIVE` with updated data*. Whether the
  order ID changes is exactly the "reversal that replaces rather than voids"
  successor question.
- **The API doc contradicts itself on the status vocabulary.** Its item-fields
  table lists `REFUND_REQUESTED` / `RESCHEDULE_REQUESTED`; its note-mapping table
  and all four response examples use `PROCESS_REFUND` / `PROCESS_RESCHEDULE`; and
  `PLAT-58738` writes `REFUND_REQUESTED` / `RESCHEDULE_REQUESTED` to
  `user_mission_progress`. Most likely the DB enum and the API enum differ and
  the field table copied the wrong one — but a consumer cannot tell.
- **Sorting is a two-block merge, not one sorted list.** The PRD says "sorted by
  active date ascending"; the API doc (newer) splits by status, sorts `ACTIVE` by
  `active_at` ASC and `PENDING`/`PROCESS_*` by `metadata.journeyEndDate` ASC,
  then merges ACTIVE-then-PENDING. Since stamp numbers follow the sequence, a
  pending order becoming active **re-numbers other orders** (PRD §10) — a
  stamp number is not permanently tied to an order.
- **Room nights are gated by mission *type*, not by vertical.** The stories read
  "for Hotel missions", which invites a wrong reading. An `ORDER_ID` mission with
  a multi-night hotel order shows **no** room nights and earns **one** stamp;
  only a `ROOM_NIGHT` mission shows the row, and then only on Hotel/Homes items.
- **`[BE]` GBV (`PLAT-58526`) is `Dropped`, and that is not a descope.** The
  sibling `[FE]` GBV story is still live, and subtask `PLAT-58741` shows one
  `/order-history` API serving all three mission types with GBV as a
  field-suppression branch. The BE story was redundant, not cancelled — .
- **The GBV story's own copy leaks from the stamp story**: *"Show a Pending icon
  next to the **stamp contribution**"* on a mission type where
  `stampContribution` is always `null`.
- **The guest note in the API doc is copy-pasted from the Mission List API.** It
  says a guest gets `summary: null` and "only the `available` tab" populated —
  neither field exists in this response schema. Guest behaviour is therefore
  undefined, not documented.
- **Design comment #285 is a supersession nobody wrote down**: tapping a
  pending stamp *used to* show a tooltip and should now navigate to Mission
  History.
- **The endpoint is stated three different ways** — subtask `PLAT-58737` says
  `/mission/history`, the API doc's PATH URL says
  `/tix-mission/api/mission/{slug}/order-history`, and its own curl example drops
  the `/tix-mission` prefix. The PATH URL is the newest; on GK the gateway prefix is `ms-gateway/`.
- **The mission detail / history FE route is not stated in any source** (the
  vault only confirms the list at `/<locale>/mission`), and mission progress
  derives from **real paid orders whose trip dates must pass**.
- **The page is read-only presentation; nothing on it moves money.** The one
  place real value is at stake is stamp revocation and re-sequencing, because
  stamps are entitlement toward a reward.
