# PLAT-56187 — [FE] Top Spender - Handle Pagination for Pending Orders History
> **Type:** Story · **Status:** In QA · **Priority:** Medium · **Parent:** [[PLAT-54035]]
> **Related:** [[PLAT-54035-v2]] · [[PLAT-54035]]
> **Jira:** https://borobudur.atlassian.net/browse/PLAT-56187

## Summary

Top 10 users with more than 25 pending orders cannot view all pending order IDs in the Top Spender transaction history because the frontend only consumes the first page of the paginated API response. Coin calculation and ranking already include all eligible orders, but the displayed transaction history is incomplete. The frontend should handle pagination to retrieve and display all pending order transactions so the history aligns with orders used in coin calculation and ranking.

## Key Points

- Backend API supports pagination for pending order transactions; frontend currently retrieves and displays only the first page.
- Users with more than 25 pending orders cannot see all pending transactions.
- Expected: frontend handles pagination and retrieves all available pending order transactions; displayed history aligns with coin calculation and ranking.
- Business impact: improves transparency, reduces confusion about missing pending orders, minimizes support and product investigation.
- Pending orders API: Top Spender `get_api_top_spender__tsId__transactions` (mission-be-svc swagger).
- Acceptance: users with more than 25 pending orders can view all transactions; verified with test account; no regression for users with fewer than 25 pending orders.

## Details
**Problem Statement**
We got report from top 10 users that users with more than 25 pending orders are unable to view all pending order IDs in the Top Spender transaction history because the frontend currently only consumes the first page of the paginated API response. This creates confusion since the coin calculation and ranking already include all eligible orders, while the displayed transaction history is incomplete.

**Current Behavior**

* Backend API supports pagination for pending order transactions.
* Frontend only retrieves and displays the first page of results.
* Users with more than 25 pending orders cannot see all of their pending transactions.

**Expected Behavior**

* Frontend should properly handle pagination and retrieve all available pending order transactions.
* Users should be able to view the complete list of pending orders returned by the API.
* The transaction history displayed to users should align with the orders used in coin calculation and ranking.

**Business Impact**

* Improves transparency for Top Spender participants.
* Reduces user confusion regarding missing pending orders.
* Minimizes customer complaints and manual investigation efforts from support and product teams.

**Acceptance Criteria**

1. Frontend correctly handles paginated responses from the pending orders API: [https://mission-be-svc.platform-cluster.tiket.com/tix-mission/swagger/index.html#/TopSpender/get_api_top_spender__tsId__transactions](https://mission-be-svc.platform-cluster.tiket.com/tix-mission/swagger/index.html#/TopSpender/get_api_top_spender__tsId__transactions)
2. Users with more than 25 pending orders can view all pending order transactions.
3. Displayed transaction history is consistent with the orders considered in coin calculation.
4. Verified using a test account with more than 25 pending orders.
5. No regression for users with fewer than 25 pending orders.
