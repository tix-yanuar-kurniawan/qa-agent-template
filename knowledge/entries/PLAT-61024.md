# PLAT-61024 — Duplicated Name Profiles Handling
> **Related:** [[PLAT-61019]] · [[PLAT-61021]] · [[PLAT-61022]] · [[PLAT-61023]] · [[PLAT-63056]] · [[PLAT-62086]] · [[PLAT-62087]] · [[PLAT-62088]] · [[PLAT-62146]] · [[PLAT-61275]] · [[PLAT-59740]] · [[PLAT-61138]] · [[PLAT-59157]] · [[PLAT-60403]] · [[PLAT-59738]] · [[PLAT-52095]]

## PRD Summary

Today the create API refuses a duplicate profile name (it silently merges into the existing
one), while the edit API lets two secondary profiles end up with the same name. The epic
allows a duplicate name only after the user confirms it. Four child stories ([BE] PLAT-61019,
[FE] PLAT-61021, [iOS] PLAT-61022, [Android] PLAT-61023) carry identical AC, plus a QA
placeholder (PLAT-63056). All were Ready for QA on 2026-11-11, with APK/iOS builds in the
epic comments (2026-11-09).

- **My Account, add (Case 2).** Once first and last name are typed, the system checks for the
  name. If another secondary profile has it, a dialog offers "continue to create new" or
  "save as the profile whose name is taken".
- **My Account, edit (Case 1).** Renaming a secondary profile to a taken name shows a dialog:
  save the profile being edited, or save the changes to the profile whose name is taken.
- **Name match ignores first/last placement.** "Jane Doe" + empty last name is the same as
  "Jane" + "Doe".
- **More than one match.** The profile with the latest update timestamp is the target.
- **Booking form (req 1b).** Adding a traveller with an existing name **automatically
  updates** the existing profile, with no dialog. With more than one match it updates the
  latest-updated one.
- **Main profile (Case 3).** Renaming it in UNM Account Center to a secondary's name updates
  the main profile and leaves the secondaries as they are.

**Technical design** — Confluence "Duplicate Name Profile Handling" (v4, 2026-09-28; its
Jira-ticket field points at [[PLAT-59740]]), referenced by the BE subtasks:

- New read-only check-duplicate endpoint:
  - It returns the matching profiles newest-updated first, each as
    `{id, accountFirstName, accountLastName, updateTimestamp}`.
  - An empty `data` list means no conflict and comes back as `SUCCESS`, not an error.
  - Errors: `UNAUTHORIZED` when there is no `X-Account-Id`; `FAILED_EMPTY_NAME` when both
    names are blank.
  - It is not served from the Redis profile-list cache.
- `allowDuplicateName` on `POST /v2/profiles/b2c`: absent/`false` auto-merges (today's
  behaviour), `true` always inserts. A positive `profile.id` routes to update ("Update
  existing").
- Deterministic match: the blind index, active profiles only, **primary excluded**, **exact
  first AND last name equality**, sorted by `updateTimestamp` desc. The booking form uses this
  through `POST /tix-profile-core/profiles` (non-flight) and `POST /v2/profiles/b2c?source=flight`.

## Key Learnings

- **Reconciled the source.** No change log or Q&A table. The four child descriptions are
  byte-identical. The real amendments are in the subtasks (created 2026-10-08 to 10-23) and the
  Confluence TDD:
  - FE PLAT-61275 covers only "My Account profile **creation**" confirmation.
  - FE PLAT-62146 adds client-side detection with **name normalisation for swapped
    placement**.
  - BE PLAT-62086/87/88 add the endpoint, the flag and the deterministic rule.
- **Match-rule contradiction — the headline risk.** The TDD and PLAT-62086 keep "exact first
  AND last name matches only", which drops placement-swapped names. The PRD (Case 1/2 a.ii)
  and PLAT-62146 say placement is ignored.
  - The booking form has no FE layer, so a placement-swapped traveller will **insert**, not
    merge. This needs a PM answer.
- **Endpoint path drift.** TDD v4: `POST /tix-profile-core/v2/profiles/check-duplicate`.
  PLAT-62086 (2026-10-22): `POST /tix-member-core/v3/profiles/check-duplicate`.
- **Edit flow has no BE guard.** The TDD lists "Edit with a duplicate name: no check at all" as
  today's problem and adds nothing to the edit endpoint. Case 1 therefore depends entirely on
  the FE calling check-duplicate before saving an edit.
- **The fate of the edited profile after "Edit existing Jane Doe": resolved 2026-11-11.** The AC
  says "save the changes for profile 200 instead". The design says "Replace: all data previous
  passenger" and the snackbar says "combine". The user confirmed the behaviour seen on Android
  and DWEB is intended: the existing Jane Doe opens with her own data, Save updates her only,
  and the edited profile (Mary Smith) is left as is. The snackbar wording is misleading and is
  with copywriting.
- **">1" vs ">2".** Req 1b.i says ">1 profile under the same name"; Cases 1/2 say ">2
  profiles". Read as "more than one matching profile besides the one being edited".
- **The TDD admits the merge is lossy:** "a thin payload can blank the stored salutation and
  gender". Nothing in the epic fixes it, and the booking-form auto-update is now the *wanted*
  path. Raise it with the PM: auto-merging
  a booking traveller into a saved profile can wipe fields the booking form never sends.
- **The primary profile is excluded from matching** (TDD/PLAT-62088). The owner's name never
  triggers the dialog. A booking traveller with the owner's name inserts a **new
  secondary** rather than touching the main profile.
- **Cross-flow findings from the surface map:**
  - Family Group's own duplicate dialog ([[PLAT-61138]], "No, it's different") must send
    `allowDuplicateName: true`, or the new BE silently merges the "different" person into the
    existing one.
  - The passport-scanner autofill ([[PLAT-59738]]) changes the names without typing.
  - Deleted or inactive profiles ([[PLAT-52095]] cleanup) must not match.
- **Copy is design copy.** The design status is Completed, but comment #148 is open on the
  button labels.
- **Questions for the PM / dev:**
  1. Which match rule is live in My Account: placement-insensitive (PRD/FE) or exact first AND
     last (TDD/BE)? And for the booking form?
  2. ~~After "Edit existing Jane Doe", what happens to the profile that was being edited?~~
     Answered 2026-11-11: it is left as is; only the existing profile is updated.
  3. Does the duplicate check fire on passport-scan autofill?
  4. After "Add new passenger", does Save re-trigger the dialog? Values typed before the
     dialog in the add flow: are they carried into "Edit the existing"?
  5. Which check-duplicate path is live?
  6. Is the lossy auto-merge acceptable on the booking form?
  7. How is the dialog dismissed, and what happens then?
  8. Is name comparison case- and whitespace-insensitive? "Normalise" is not defined.

## Observed behaviour

- check-duplicate is live at `/tix-member-core/v3/profiles/check-duplicate` (edit adds
  `excludeProfileId`).
- First/last placement **is** ignored by the backend match.
- After "Edit existing", the edited profile is **kept** (untouched).
- A name with no surname is stored split ("Jane"/"Doe").
- The flight-checkout auto-merge wipes the saved passenger's phone and replaces the email with
  the account email.
