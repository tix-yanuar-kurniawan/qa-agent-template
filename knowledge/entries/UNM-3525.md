# UNM-3525 — Support Unified BCA Blibli Tiket Cobrand Card

## PRD Summary
UNM-side scope of the Unified BCA Blibli Tiket Cobrand Card program. When a BCA cobrand credit card is approved, BCA calls the UNM Registration API with **phone and email only** — UNM must auto-register a new member or map an existing one, using phone as the primary matching key. The scope covers: account matching logic (11 documented cases), name derivation via email sanitization, suspend/FDS handling, BCA-holder status management (customer redirect + admin dashboard remove menu with password challenge), existing-user mapping via entity, account-update handling (deletion warnings, card closure, phone claim/unverification impact on mapping and point injection), removal of the old entity-proxy integration, audit-history logging (`MAP_BCA_COBRAND`), welcome email, and the cobrand landing-page redirect. Source: two PDF PRDs (Main PRD = in scope, Bigger Scope PRD = context). The epic lives on `gdncomm.atlassian.net` (not reachable via the connected Atlassian MCP), but was later inspected via an authenticated browser session — the epic + 15 child stories were confirmed to be a platform-split breakdown (`[BE]`/`[FE]`/`[FE Panel]`) of the Main PRD, with each story copying the relevant FR verbatim.

## Key Learnings
- **Phone is the primary matching key**, email secondary — the matching table produces different outcomes (map vs. new account, email verified vs. empty vs. unchanged) depending on which of phone/email match and whether they point to the same or different accounts.
- **Name derivation is deterministic**: strip domain → remove digits → replace special chars *between* alphabets with space → drop special chars *not* between alphabets; use as title-case name if ≥4 chars, else default `Blibli Tiket User`; truncate to 60 chars. Existing-account names are never overridden.
- **Idempotency & many-to-one**: re-registering already-mapped credentials must not error or re-map; one account can hold multiple cards (each card eligible for its own welcome bonus). BCA passes no card identifier, so UNM marks holder status only — it cannot map a specific card to an account (acknowledged risk).
- **Cobrand holder is a special user segment** (consistent with [[PLAT-53384]]) with exception rules — suspended/FDS-blocked credentials are still registered/mapped, unlike the normal login/registration block.
- **Deletion is gated in ordered steps**: pending CS ticket/order/paylater blocks first; only when clear does the BCA-holder check run and surface a benefit-loss warning; deletion still proceeds. 
- **Phone claim / unverification desyncs mapping**: mapping is not updated and point injection is blocked whenever the mapped account's phone becomes unverified .
- **Jira stories can be more current than the PDF PRD** — the child stories are a verbatim FR breakdown, BUT surfaced detail absent from the PDFs: (1) holder-status management evolved from a "remove menu" into a bi-directional **Connect/Disconnect toggle** requiring a **mandatory reason** + password; (2) an explicit **audit log** `eventType: update_bca_cobrand_status` (timestamp, sourceIp, sourceIdentity, targetIdentity, detailActivity{oldStatus,newStatus,note}, activityResult); (3) member-details **history text** format; (4) a **ULP-consumable** holder-identification capability (UNM-3549); (5) welcome-email **name personalization** + migrated templates (UNM-3550). Lesson: when a Jira board is provided, verify the stories even if PDFs exist — the breakdown may carry newer implementation detail.
- **PDF text extraction silently drops strikethrough** — a removed requirement reads as a live one. When a PRD ships as a PDF, treat the **change log** and the **Q&A/decision table** as the authority on what is still in scope, and reconcile any requirement they contradict against the rendered document (see corrections below).

## Post-review corrections (2026-07-31)
Raised by the QA lead after the first pass.
These supersede the affected points above.

### FR3 item 2 "[Delete account from entity apps]" is struck through in the source PRD
Strikethrough is lost in PDF text extraction, so the requirement initially read as live. It is not. This agrees with two signals that were visible in the text and should have
been weighted higher: the PRD change log entry for **Jul 2, 2026** ("remove warning in
account deletion") and Q&A row 1's answer ("there will be no warning on user end upon
account deletion"). The rationale is Q&A row 2 — BCA cannot tell UNM when a card is closed,
so holder status may be stale and a benefit-loss warning could be simply wrong.

Only the **user/customer end** loses the warning; `[Delete account from UNM Dashboard]`
(FR3 item 3) is unaffected and still warns. The PRD uses the same "customer end" vs
"internal admin end" pairing in FR1.7.

### "External" in the matching table is legacy vocabulary
`External Email` / `External Phone` / `External Account` mean **not UNM** — the entity
account systems (Tiket, Blibli, Dekoruma, Ranch) and the values arriving from them. Per the
QA lead, UNM previously used **Debezium** to replicate into the entity databases; that was
deprecated long ago and data now streams near-instantly, so the external-vs-UNM split is
the PRD author carrying forward a distinction that no longer exists in the system.

Consequence: matching **case 8** ("email matching to a different External Account")
collapses into **case 7** ("phone & email matching to different UNM accounts") — both
resolve identically (map by phone, leave the email unchanged), so they are largely redundant.

### Matching case 10 is flagged unreachable by the PRD itself
The row carries the note *"case is not possible to happen. there's no users with empty email
and non verified phone on UNM."* The precondition may be unconstructable. Confirm the invariant still holds with the BE lead. Case 11 is the genuinely reachable unverified-phone scenario.

### There is a newer BCA registration API that the Jira epic does not reference
`POST /tix-member-core/v2/partner/cobranding-bca` on `member-core-v2.eiffel-ns.svc.tiket`
(headers `X-Client-Id: BCA`, `X-Secret-Key`, `X-Store-Id: TIKETCOM`) is the **legacy**
per-entity path — the integration FR4 wants retired. It creates the account but no unified
cobrand partner record, so the dashboard Connect action then fails. It also accepts a `name`
field in the payload, which the current design explicitly does not (BCA confirmed phone and
email only, hence the email-derivation logic) — a useful tell for which code path ran:
`uni.cobrand1@yopmail.com` should derive **"Uni Cobrand"**, so a stored name of
"Unified Cobrand" means the payload name was taken and the new logic did not run.

### Admin Connect cannot mint holders; the error leaks an internal code
Toggling BCA cobrand status to Connected for an account with no BCA partner record fails
with a red toast reading **`PARTNER_NOT_REGISTERED`**. The guard is correct — holder status
originates only from BCA registration, and inventing holders would make them ULP-privileged
(double/triple points per [[PLAT-53384]]) and welcome-bonus eligible with no card behind it.
Two real findings sit next to it: the toggle is **enabled on accounts that can never be
connected**, contradicting FR1.7's show/hide requirement, and the raw error code reaches the
admin UI, suggesting the panel has no error-code-to-message mapping.

### No same-status guard is specified for the dashboard toggle
Nothing in either PRD or the stories covers Connected → Connected or
Not Connected → Not Connected. The only idempotency rule in the epic is registration-side
(FR1.4: don't error, don't update). The toggle UI hides the gap — you can only reach a no-op
write via the endpoint directly, a double-submit inside the reason + password modal, or two
admins acting on stale state. If unguarded it degrades three documented behaviours: the history text renders "changed from Connected to Connected", the audit log `detailActivity` carries
`oldStatus == newStatus`, and `activityResult` is ambiguous for a no-op. Open question for the PM.

### Warning asymmetry between deletion and phone unverification
Dashboard deletion of a holder warns about benefit loss (FR3 item 3), but phone
unverification (FR3.6) has no warning at all despite a comparable customer outcome — the
mapping survives while point injection is blocked, so benefits silently stop. A CS agent can
honour a routine "remove my phone number" request and break a cardholder with nothing on
screen indicating it. The PRD gives no reason for the difference.
