# PLAT-59743 — Handle Earning Points for Zero Flexible Payment
> **Related:** [[PLAT-59745]] · [[PLAT-59746]] · [[PLAT-57759]] · [[PLAT-54713]] · [[PLAT-54039]] · [[PLAT-53384]]

## PRD Summary

Zero Flexible Payment (`ZERO_FLEXIBLE_PAYMENT`) orders can reach **Issued** without being marked **Paid**, so the existing earning flow — which keys off Paid — never starts. This epic switches ZFP earning onto the **order lifecycle**: pending when the order is **Issued**, issued to the user when the order is **Finished**, pending cancelled on **Cancel/Refund** before issue, and the **existing reversal** if points were already issued. Amount, eligibility, and earning type stay the current rules ([[PLAT-54039]], [[PLAT-53384]]). Child stories: [[PLAT-59745]] `[BE]` holds the ACs; [[PLAT-59746]] `[BE]` Solutioning has no testable ACs. Epic platform is Backend. Related payment work [[PLAT-57759]] already releases *applied* (redeemed) points on ZFP cancel — different pool from this earning lifecycle. No Figma.

## Key Learnings

- **Child AC "when the user has paid and the order is issued" does not mean payment status = Paid.** The epic problem is that ZFP reaches Issued *without* Paid. Reading the AC literally would recreate the bug. "Has paid" is completing the ZFP checkout (IDR 0 upfront). Pending is generated at **Issued**, including when payment status is still not Paid. A later subsequent payment that *does* set Paid must not issue early; only **Finished** issues.
- **Epic body "pending after the order is created" is superseded by [[PLAT-59745]].** Created-but-not-Issued must not generate pending.
- **Cancel/refund of pending is a pre-Finished branch.** The tiket machine is `waiting for payment → processing e-ticket → e-ticket issued → finished | refund | reschedule` with the last three mutually exclusive ([[PLAT-54713]] heuristic). Refund/cancel happens **from Issued**. Reversal after issue is stated by the AC, but it is unclear whether Finished can be refunded.
- **[[PLAT-57759]] is a different pool.** That story returns *redeemed* TixPoints on ZFP cancel. This epic is *earning*.
- **[[PLAT-59746]] Solutioning has no testable ACs** (timeline/constraints/task breakdown). Same for any solutioning-only child.
- **No earning endpoint is named.** Hotel ZFP is inferred from [[PLAT-57759]], not from this epic.
- **Backend-only epic:** no FE child, no points-history path in the source.
- **Related prior knowledge:** [[PLAT-54713]] state machine and pending-then-issue; [[PLAT-54039]] existing calculation / promo-GV minimal earn; [[PLAT-53384]] eligibility exclusions still apply to ZFP; cobrand exception heuristic (unclear whether cobrand can use ZFP).
