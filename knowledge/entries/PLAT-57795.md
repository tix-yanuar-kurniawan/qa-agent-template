# PLAT-57795 — [BE] Development for Supporting Corporate Multi-Entity
> **Related:** [[PLAT-57216]] · [[PLAT-58696]] · [[PLAT-58697]] · [[PLAT-58702]] · [[PLAT-58703]] · [[PLAT-59667]] · [[CRP-6807]] · [[CRP-7021]] · [[CRP-7023]] · [[CRP-7032]] · [[UNM-3525]]

## PRD Summary

Member / Platform slice of Corporate Multi-Entities 2.0. One tiket.com account books under another legal entity in the same corporate hierarchy without logging out. Member persists Phase 2 corporate context (`corporateID`, `originalCorporateID`, `parentCorporateID`, `resellerType`, `loginRedirection`) at login, replaces it wholesale on entity switch, and exposes it through `/session/validate`; API Gateway injects the four canonical headers so verticals evaluate policy, fares, promo, payment and order ownership against the **assigned** entity rather than the booker's home entity.

Three endpoints carry the work: login (`exchange-token/session-id` and `/service-ticket`), the member-core sync proxy (`PUT /v3/corporate/session/sync`), and member-session `PUT /v2/session/deactivate-others`. Gateway items G1–G7 consume the output.

This set is **Member PoV only**. Corporate `GET auth/corporate/check`, `PUT /tix-corporate/booking-center/auth/sync` and `PATCH /tix-corporate/corporate-dashboard/multi-entity/sessions` are setup and production triggers. Flight, Accom, Pricing, Promo, Payment, the booking-center UI, and employee/RBAC management are out of scope.

## Key Learnings

- **`resellerType` has no documented producer — the highest-value finding.** The Member field table (spec, 2026-08-11) marks Corporate `auth/corporate/check` as the source with "✅ new". The Corporate-side proposed response on [[CRP-7023]] and on *[WIP] Multi Entities Phase 2* (v81, **2026-09-09**) lists `loginRedirection`, `originalCorporateID`, `parentCorporateID` as the new fields and **no `resellerType` at all**. Meanwhile G1 removes the hardcoded `XCorporateResellerType` constant and D12 makes the gateway read it from validate only. If Corporate never sends it, `x-reseller-type` regresses from a constant to empty for every corporate session. It should be raised against [[CRP-7023]].
- **The Q&A answer lowers the weight of OTA, it does not kill it.** *Vertical Related* (v31, 2026-09-07) answers "will keep X-Reseller-Type as is and **not adding value** `OFFLINE_TRAVEL_AGENT`". Scoped to **Each Vertical**, so Member still stores and the gateway still forwards whatever Corporate sends — but nothing downstream acts on the OTA value. So a spoofed OTA value has no downstream consumer.
- **The sync contract page gained two failure codes on 2026-09-07.** [Session Sync](https://borobudur.atlassian.net/wiki/spaces/MEM/pages/4907302973) v7 now documents `SESSION_ERROR` at **HTTP 200** and `INTERNAL_SERVER_ERROR` at 500 alongside `SESSION_NOT_FOUND` at 200. Two distinct outcomes on 200 mean Corporate cannot branch on status
- **A later API contract outranks the story AC for response shape.** Task 2b's AC and the Endpoint Change Spec still promise `sessionUpdated` + `deactivatedSessionCount` on sync; the contract page settled on `{ code: SUCCESS, data: { success: true } }`.
- **`deactivate-others` contradicts itself inside one page.** Its response-contract JSON shows `data.success` only, while the same page's AC, its sequence diagram, and [[PLAT-58702]] all name `deactivatedSessionCount` — three places to one.
- **The contract page's request-header block is a copied gateway template.** It lists `Authorization`, `tixtoken`, `tixsession`, `X-Account-Id` on an endpoint D10 specifies as **no auth**. Treated as a doc leak, not a requirement.
- **The sync proxy now has two Corporate callers, not one.** `PUT /tix-corporate/booking-center/auth/sync` (booking-center, mandatory `X-Account-ID` + `X-Session-ID`, body `{corporateID, travelerID}`) and `PATCH /tix-corporate/corporate-dashboard/multi-entity/sessions` ([[CRP-7032]], body `{corporateID}`) both land on the Member proxy. [[CRP-7021]] adds `x-session-id` at the gateway specifically so Corporate can pass the session to Member. Both are setup, but they explain why `sessionId` is mandatory on the Member body.
- **The gateway's int64 formatting turns a missing id into `0`.** The example Go code calls `strconv.FormatInt` on `OriginalCorporateID` / `ParentCorporateID`. On a pre-migration or partial blob an unset field is forwarded as a literal `0`, which no vertical can distinguish from a real entity id. G6 says "handle nil gracefully".
- **Parent Jira text is stale and stayed stale.** PLAT-57795 and [[PLAT-57216]] still say `chargedCorporateId` / `chargedEntityId`; [[PLAT-57216]] has not been edited since 2026-07-30. The live vocabulary is `corporateID` (assigned/active) + `originalCorporateID` (home) + `parentCorporateID`.
- **D2 and D11 are dead.** D13 (2026-08-11) removes `divisionID` / `accessRoleID` from persistence, sync payloads and gateway injection while **retaining** `accessRoleName` and `accessRolePermission` for display. D12 makes `x-reseller-type` validate-sourced only. [[PLAT-58695]] was split into [[PLAT-58702]] + [[PLAT-58703]] and marked Invalid.
- **`accessRoleName` is removed from the login body but retained in the blob.** The 2026-08-20 to-be example drops it from the FE response; the field table keeps it "retained for display" on validate. Both are true.
- **Path aliases still unresolved.** The contract table says `/tix-member-core/v3/corporate/session/sync`; its own curl says `/tix-member-core-v2/v3/...`. A swagger note also shows `/tix-member-core/v3/auth/unm/service-ticket` without `exchange-token`.
- **D5 is a UNM non-event; D10 (no auth) is specified.** Entity switch must not invalidate UNM sessions ([[UNM-3525]] is related for that reason). The missing auth matters in one place: a malformed body must not be able to mass-deactivate an arbitrary `accountId`.
- **Gateway headers appear on no Member response.** They are set on outbound gateway calls ([[PLAT-58697]] is a subtask of this story), and the observation path is `UNKNOWN` (needs a vertical-side echo or a gateway log).
