# PLAT-59094 — Loyalty x Tiket FDS Orchestration Layer Integration
> **Related:** [[PLAT-59095]] · [[PLAT-59096]] · [[PLAT-59342]] · [[PLAT-60902]] · [[PLAT-59098]]

## PRD Summary
Loyalty points are being abused: Pay at Hotel bookings complete missions and are then cancelled, and Instant Points Cashback is sometimes not revoked after a refund. Loyalty has no consistent pre-check on whether an activity is legitimate. This phase makes Loyalty call Blibli FDS through the Orchestration Layer, synchronously, at two points: before points are credited and before points are deducted for a redemption. The Orchestration Layer forwards the event and returns the raw verdict. What Loyalty does with the verdict, FDS rules and scoring, and reversal on cancel or refund are all out of scope.

Two functional child stories, both `[BE]`:
- [[PLAT-59095]] — credit event. `event_id = "loyalty_points_earned"`, `mode = "sync"`. Fields: `unm_id`, `points_to_inject`, `point_type`, `earn_source` (derived from `point_type`, overridable from the Tech Support and Rewards Hub dashboards), `mission_id`, `referrer_user_id`, `order_id`, `order_detail_id`, `device_id`. `device_id` is sent only for user-triggered credits.
- [[PLAT-59096]] — redemption event (non-payment). Identifier `loyalty_points_redeemed`, `mode = "sync"`. Fields: `unm_id`, `points_to_redeem`, `order_id`, `device_id` (always required, FE relays it).

[[PLAT-59342]] is tech solutioning with no acceptance criteria. [[PLAT-60902]] is the QA tracking story. No `[FE]` or `[Panel]` story exists, although `device_id` is captured by the FE/Apps.

## Key Learnings
- **Nothing in the epic says how to observe the FDS request.** There is no log, trace or Orchestration Layer inspection path, and the verdict handling is out of scope.
- **Two stories disagree on the event identifier key.** PLAT-59095 uses `event_id`, PLAT-59096 uses `event_type`.
- **PLAT-59096 has a typo and a contradiction.** The field table says `payload_order_id` but the example uses `payload.order_id` (the example is taken as authoritative). The "Always sync" rule sits beside a note "Can send to FDS when apply async"; the note is unresolved.
- **User-triggered vs system-triggered is not classified for every issuance type.** The scope list names Mission rewards, Extend Points and Review as user-triggered, and Points earning, Rewards Hub and IPC/Subsidy as system-triggered. Tech Support Dashboard injection is shown without `device_id` in the PLAT-59095 example. Partner injection API is unclassified, so whether it carries `device_id` is unknown.
- **"Points from points extension" and "Extend Points" are treated as one flow**. The epic does not say how a user triggers it.
- **Rewards Hub Dashboard override has no stated value.** The story says it may override `earn_source` like the Tech Support Dashboard but gives no value.
- **Mission via Rewards Hub (PLAT-59098) overlaps this epic.** If Mission now credits through Rewards Hub, one claim might produce one or two FDS events. Neither epic says which; the count is `UNKNOWN`.
- **Payment use of points is not covered.** PLAT-59096 says "non payment"; whether spending points at checkout also sends an event is unstated.
- **Out of scope:** all verdict-dependent behaviour (block, withhold, reverse, allow), FDS rules and scoring, and refund/cancel reversal.
- **Not covered, behaviour UNKNOWN:** redemption with a missing `device_id`; FDS or Orchestration Layer timeout or error on the sync call; redelivery of the same credit (does it resend, with the same `reference_id`?).
