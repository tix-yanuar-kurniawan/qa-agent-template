# PLAT-59098 — Centralize Mission Reward Injection via Rewards Hub
> **Related:** [[PLAT-59099]] · [[PLAT-59100]] · [[PLAT-59101]] · [[PLAT-56247]]

## PRD Summary
Mission currently has its own reward-injection mechanism, separate from Rewards
Hub (the centralized loyalty engine other verticals already use for Points/GV
and device-ID-based fraud limits). This epic moves Mission onto Rewards Hub as
the single injection mechanism. Points claims are unaffected for the user; GV
claims move from a static, shared Promo Code to a unique GV code generated
per-claim by the GV Service via Rewards Hub. Three functional child stories
carry the work: [[PLAT-59099]] (BE — Mission calls Rewards Hub to disburse,
using a Rewards Hub Campaign ID per reward/milestone), [[PLAT-59100]] (Panel —
Mission Dashboard gets a searchable "Rewards Hub Campaign" field as an
alternative to the existing manual reward config, Phase 1), and [[PLAT-59101]]
(FE — the claim request forwards the user's Device ID so Rewards Hub can apply
its existing fraud-prevention limit; an over-limit device fails the claim
without marking the reward claimed). Three further child stories
(PLAT-59341/59130/59129) are tech-solutioning tasks with no acceptance
criteria; PLAT-60240 is the QA tracking story itself.

## Figma Design Summary
One section (`Section / Reward`, node `6050:31355`) mocks the Mission
Dashboard reward-config panel in the Panel: a **Single**-reward row showing
four states (Default/Points, existing Promo config, field-level Error, and
"Reward using reward hub"), an **error-wording table** (11 rows covering
Reward Title EN/ID empty + max-40, Point Amount empty, Promo Code
empty/duplicate, Promo ID empty/not-found, Reward Quota empty), a **"Search
campaign ID" field-behavior strip** (empty → loading → not-found → results
list → selected), and a **Milestone** column repeating the same reward block
per milestone plus notification checkboxes (Milestone progress / Milestone
reward achieved, each Email + Push). The "Configure reward manually" toggle is
annotated **"Default is Toggle OFF"** — i.e. the Rewards Hub Campaign search is
the default config source, not the legacy manual fields.

## Key Learnings
- **In the old Mission implementation, a Promo reward *is* an already-created GV.** This
  equivalence holds **only in the Mission context**: in the wider Promo & GV system the
  two are separate mechanisms and must not be treated as interchangeable. Mission has
  only two reward types today, **Points** and **Promo** (Panel fields: Reward Type,
  Quota Point Type, Point Amount, Promo ID, Promo Code; claim path whitelists the user
  to the promo or injects points). There is no separate GV type in Mission's code — a
  "GV reward" is just a Promo whose code was created in advance and is shared by every
  claimer. Under Rewards Hub the GV is **generated dynamically at claim time**, one
  unique code per successful claim, by the GV Service. So "GV" becomes a distinct type
  only on the Rewards Hub path (the Figma mock already names a `Type=GV` variant);
  manual-mode Promo rewards keep the shared-code behaviour until Phase 2 removes them.
  Source: PRD Background + PLAT-59099 "For GV" block; confirmed by the QA owner.
- **A real ambiguity between two child stories, flagged rather than resolved by
  invention.** [[PLAT-59099]] states Rewards Hub becomes the injection
  mechanism for *all* Missions, while [[PLAT-59100]] Phase 1 still lets an
  admin pick "existing Mission reward configuration" as a config source. Read
  together the likely intent is that Rewards Hub is always the actual injector,
  and the manual fields just feed it a type/amount instead of a Campaign ID —
  but neither story says so. Which backend mechanism performed the
  injection is not visible from any UI.
- **Quota-exhaustion and device-over-limit states have no seeding path
  in either story.** Reaching them needs Rewards Hub team
  support to pre-configure a campaign at zero quota or a device already over
  its limit.
- Reward injection is the system under change in this epic, not a downstream
  dependency as in [[PLAT-56247]].
- Panel entry point is `Panel > Loyalty > Mission Config > <mission> edit >
  Reward section`; only `/admin/care/loyalty/mission-config` (list) and
  `.../center` (banner/sequence config) are confirmed URLs, not the per-mission
  reward-config sub-page.
