# PLAT-53961 — Dynamic Missions in Welcome Rewards
> **Source:** Jira Epic · Confluence PRD · Figma · **Jira:** https://borobudur.atlassian.net/browse/PLAT-53961
> **Related:** [[PLAT-53967]] · [[PLAT-53968]] · [[PLAT-53969]] · [[PLAT-54108]] · [[PLAT-54109]] · [[PLAT-54110]] · [[PLAT-55685]] · [[PLAT-55867]] · [[PLAT-54052]] · [[LoyaltyMissionSlugProgressGET]]

## Summary
Welcome Rewards (shown once during onboarding to drive activation via Points, GV, Free Tier Upgrade, and Promo Codes) is enhanced with **contextual, dynamically-configured missions** so new users have a reason to revisit their rewards after onboarding. On a fresh install, after onboarding, the user sees the **Welcome Rewards Bottom Sheet**, which loads a configuration selected by user acquisition source (**Campaign ID → UTM Source → Default**). Each mission module in the selected config is mapped to a Loyalty mission by **Mission ID**; missions not found in Loyalty are hidden. The system auto-sets the user as **eligible for all missions** in the config by calling Loyalty with **Mission ID + Account ID** once all required data is available. Tapping a module opens the **Mission Detail Page** (or routes an unauthenticated user through Login/Register first, then returns to Welcome Rewards). This epic (`PLAT-53961`, project **PLAT / Platform - Eiffel**, status **Done**) covers **Phase I** only; the PRD also specifies **Phase II** (a dynamic New User Page on the Homepage) which is out of scope here.

## Key Points
- **Scope:** Phase I = *Dynamic Missions in the Welcome Rewards Bottom Sheet*. Phase II (dynamic New User Page on Homepage) is documented in the PRD but out of scope for this epic. Target release **Q2 2026**.
- **Config source priority:** `Campaign ID` > `UTM Source` > `Default`. The chosen config determines which mission modules appear.
- **Loyalty mapping:** Every mission in the config must map to a Loyalty mission via **Mission ID**. Missions not present in Loyalty are **not displayed**.
- **Auto-eligibility:** System sets the user eligible for **all** missions in the selected config (not just one) by calling the Loyalty eligibility API with **Mission ID + Account ID**, once all required data (incl. Account ID) is available.
- **Logged-in flow:** tap module CTA → **Mission Detail Page**; back navigation returns the user to Welcome Rewards.
- **Logged-out flow:** tap any module → **Login/Register** → on success, return to Welcome Rewards → once Account ID is available, auto-set eligibility for all missions.
- **Mission module anatomy (Phase I):** Mission Icon (BE config), Mission Title (BE config), Mission Subtext (BE config), CTA Button. UI has **Not Joined** and **Joined** states.
- **Trigger:** fresh install → finish onboarding → Welcome Rewards Bottom Sheet appears.
- **Platforms delivered:** Backend, iOS, Android (plus a solutioning spike per platform and a multi-platform QA story). No responsive/FE-web story in this epic.
- **Related eligibility API:** [[PLAT-55867]] *[BE] Get Mission Detail & Eligibility API* defines the mission/user status model and response payload used by the mission detail experience.
- **Status of work:** Epic **Done**; delivery custom fields show *New Feature*, *Shipped*, health *Green*. Ran across Eiffel Sprints 79–83.

#### Phase I — Mission Module on Welcome Rewards (in scope)
*As a user, I want to see and join missions on Welcome Rewards so I can participate in mission programs.*
Given a fresh install, When onboarding is finished, Then the Welcome Rewards Bottom Sheet is shown.

Acceptance criteria:
1. System loads the Welcome Rewards configuration by user source: **Campaign ID → UTM Source → Default**.
2. If the selected config contains one or more mission modules **and the user is logged in**:
   - Each mission must map to a Loyalty mission via **Mission ID**.
   - Missions not available in Loyalty must **not** be shown.
   - System auto-sets the user **eligible for all missions** in the config by calling Loyalty (**Mission ID + Account ID**) once all required data is available.
3. Clicking the module button redirects to the **Mission Detail Page**.
4. Navigating back from the Mission Detail Page returns the user to Welcome Rewards.
5. If the user is **not logged in**: clicking any module redirects to **Login/Register**.
6. After successful login/register: redirect back to Welcome Rewards; once Account ID is available, auto-set eligibility for all missions. The eligibility request must include **Mission ID + Account ID**.
7. Each mission module consists of: **Mission Icon** (BE config), **Mission Title** (BE config), **Mission Subtext** (BE config), **CTA Button**.

Worked example from the PRD:
- **Config A (Campaign ID):** `campaign_id = CNY2026` → Mission A (ID 101), Mission B (ID 102), GV 1.
- **Config B (UTM Source):** `utm_source = tiktok_ads` → Mission C (ID 201), Mission D (ID 202), GV 2.
- **User Case 1:** installs with `utm_source = tiktok_ads` → becomes eligible for **Mission C & D**; is **not** eligible for and does **not** see Mission A & B.
- UI states: **Not Joined** and **Joined**.

#### Phase II — Dynamic New User Page on Homepage (out of scope for this epic; documented in PRD)
- **Dynamic module New User Page:** Given a user visits the Homepage, then show the New User Page dynamic module.
  - Logged out: see available modules (mission + non-mission) by config (UTM / Campaign ID / default); clicking a module → Login/Register; after auth → back to Homepage; page re-evaluated by Account ID.
  - Logged in: show the New User Page only if ≥1 module is available; module config is **bound per user**; if no modules, do not display. If no existing config, the system generates config by Campaign ID / UTM / Default and **persists** it to the user; if config exists, all modules derive from the user's config and **UTM/Campaign must not override** it.
  - Module visibility rules differ for mission vs non-mission modules.
  - **Display order:** Mission → Points → GV → Promocode → Banner → FTU.
- **Mission module on New User Page:** show missions the user is eligible for or has joined.
  - Eligible but not joined → mission appears only **X days after** becoming eligible; clicking marks the user **JOINED**.
  - Joined → only show missions where the countdown has not ended **OR** not all rewards claimed; click → Mission Detail Page.
  - Remove a mission when it has **expired** OR the user has **completed AND claimed all rewards**.
  - Module content: Mission Icon, Mission Name, Countdown End Time (if joined), CTA Button.
  - Loyalty mission-expiry removal: eligible-but-expired after X days (never joined); joined but dynamic mission end date expired; joined but dynamic claim-rewards end time expired.
- **Non-mission module on New User Page:** Points, GV, Promo Code, Banner, FTU the user is eligible for.
  - Logged in: only show modules eligible per segmentation — **WrobSegmentNewUser**, **WrobSegmentUserWithoutTransaction**; visibility evaluated per module; bound to user by Account ID; module state (countdown, claim status) persists across sessions; expired time-sensitive modules may still show while the user stays in-segment but as **non-interactive**; if the user exits the segment, all modules are hidden even if still valid or unclaimed.

### Related API — PLAT-55867 [BE] Get Mission Detail & Eligibility API
Backend · assignee Alvin Setiawan · status **Dev Done** · *relates to* this epic.

- **Contract:** Given a vertical service has `accountId` + `missionId`, When it calls the Get Mission Detail & Eligibility API, Then Loyalty evaluates eligibility, returns mission details, and returns the user's status in the mission.
- **Mission status:** `SCHEDULED` (before start), `ACTIVE` (running & quota available), `OUT_OF_QUOTA` (reward quota exhausted), `ENDED` (end date passed), `CLAIM_EXPIRED` (claim end date passed).
- **User status:** `NOT_ELIGIBLE` (fails targeting), `INACTIVE` (eligible, not enrolled), `ACTIVE` (enrolled), `COMPLETED` (finished, reward not claimed), `CLAIMED` (finished and claimed).
- **Mission info fields:** `missionId`, `missionSlug`, `missionName`, `missionStatus`, `startTimestamp` (epoch s), `endTimestamp` (epoch s), `rewardClaimEndDate`, `missionType` (`ORDER_ID` | `ROOM_NIGHT` | `GBV`), `targetValue` (required stamps / room nights / GBV), `minimumTransactionAmount` (if configured), `eligiblePaymentMethods`.
- **User info fields:** `userStatus`, `currentProgress` (progress toward the mission target).

### Key learnings
- Config selection is a strict priority (Campaign ID > UTM Source > Default), with fallbacks down the chain.
- Eligibility is auto-set for **all** missions in a config, not just the tapped one, and missions missing from Loyalty are filtered out.
- Login-redirect round-trip is core: tap module (logged out) → login/register → return to Welcome Rewards → eligibility set once Account ID exists.
- Mission/user status matrix (from [[PLAT-55867]]) drives detail-page behavior (SCHEDULED/ACTIVE/OUT_OF_QUOTA/ENDED/CLAIM_EXPIRED × NOT_ELIGIBLE/INACTIVE/ACTIVE/COMPLETED/CLAIMED).
