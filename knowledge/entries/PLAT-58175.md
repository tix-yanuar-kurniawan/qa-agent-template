# PLAT-58175 — [BE] Top Spender Challenge Logic Improvement - Booking Eligibility Validation
> **Related:** [[PLAT-58211]] · [[PLAT-54035]] · [[PLAT-54037]] · [[PLAT-54038]] · [[TOP-SPENDER-GAMIFICATION-V2]] · [[TOP-SPENDER-V2-PHASE-3]] · [[PLAT-52848]]

## PRD Summary

A correctness fix on the Top Spender **Challenge** calculation. Today the calculation does not fully validate whether a transaction is eligible against the challenge period and the transaction lifecycle, so users receive spending value from bookings that should never have counted — which then distorts mission reward calculation and the leaderboard.

Six acceptance criteria define the new eligibility gate:

- **AC1 — Booking Order Date.** `Challenge Start Date ≤ Booking Order Date ≤ Challenge End Date`, otherwise the booking is ignored.
- **AC2 — Booking Finish Date.** The completion event (completed / stayed / flown) must also fall inside the same challenge period. A booking placed during the challenge but completed after it ends is **not** eligible.
- **AC3 — Refund.** A refunded booking contributes **0** and is excluded from the leaderboard.
- **AC4 — Reschedule.** A rescheduled booking contributes **0** and is excluded from the leaderboard.
- **AC5 — Eligible transaction.** Order date in period + finish date in period + neither refunded nor rescheduled → the amount is included in the user's accumulated Top Spender amount.
- **AC6 — Claim reward date.** The user can only claim after passing the challenge, and only while the challenge is still running: `Challenge Start ≤ passed date ≤ claim date ≤ Challenge End`.

Sub-task [[PLAT-58211]] (Done) carries the implementation: *"Fix query to get eligible challenges for order that has order timestamp & order finished within period"* — note **order timestamp**, i.e. the comparison is timestamp-level, not calendar-date-level, and the query resolves the set of *challenges* an order is eligible for (plural).

## Order Lifecycle (not in the ticket — supplied by QA)

```
waiting for payment → processing e-ticket (payment success) → e-ticket issued → finished | refund | reschedule
```

`finished`, `refund` and `reschedule` are **mutually exclusive terminal states** branching from `e-ticket issued`. **A finished order cannot be refunded.** It is recorded here because the ticket never states it.

## Key Learnings

- **The story is labelled `[BE]` with `Platforms: Backend`, but its effects are user-observable.** The accumulated spending, the challenge progress, the leaderboard rank and the claim CTA all already have a UI from the shipped [[PLAT-54038]] `[FE] Top Spender Challenge`.
- **AC3 and AC4 are almost entirely subsumed by AC2, because of the lifecycle.** Since a booking only counts once it is `finished`, and `refund` / `reschedule` are sibling terminal states that a finished order can never enter, a refunded or rescheduled order **never had a finish date to begin with** — AC2 already excludes it. AC3/AC4 are therefore defensive guards, not independent scenarios. The consequence: "a counted booking is later refunded / rescheduled, so the amount is deducted and the leaderboard recalculated" **cannot happen**. The only refund/reschedule scenario is "order is refunded or rescheduled *from the e-ticket issued state* and therefore never contributes at all".
- **The sharp question the ACs never ask is *at which order status spending accrues*.** The bug being fixed exists because value is credited before completion, so at `e-ticket issued` the order must contribute nothing, and the amount appears only when the order flips to `finished` inside the period. Likewise an unfinished order can never push a user over the target and unlock the reward — the provisional-progress trap from the accumulated heuristics.
- **Reschedule exposes an undefined rule.** A rescheduled order is replaced rather than simply voided, so the real question is how the *replacement* order is evaluated — and specifically whether it carries the original order date or the reschedule date. That decides eligibility whenever a reschedule happens near a period boundary, and the PRD does not say.
- **AC6 contains an unreachable clause.** "User passed the challenge **after** the challenge end date" cannot be constructed, because AC1/AC2 already prevent any booking from counting once the period closes — so the user can never cross the target after `Challenge End Date`. AC6 is meaningful only as (a) claim inside the period succeeds, (b) claim after the period is rejected, (c) claim below target is rejected.
- **"Reward Claim Active" in the AC6 formula is never defined** as a configurable field. It was read as "the moment the user submits the claim", which is the only interpretation that makes the chained inequality testable.
- **The reschedule rule contradicts the general heuristic and the PRD wins.** The accumulated heuristic for order-driven progress says a reschedule that keeps the completion date *inside* the window retains the item. This PRD is unconditional: rescheduled bookings contribute 0 regardless. So a reschedule staying inside the period still contributes 0.
- **Undefined edges:** *partial refund* on a multi-pax or multi-room order (the PRD only says "refunded", and a partial refund is the one path that could plausibly touch an order after completion), and whether the reschedule *replacement* order inherits the original order date. Both need a product answer. The earlier open question about a refund arriving after the reward was claimed is now closed by the lifecycle — a finished order cannot be refunded, so a claimed reward cannot be undermined by a later refund.
- **Prior rules inherited from the shipped release** ([[TOP-SPENDER-GAMIFICATION-V2]], [[PLAT-54035]]): since this change touches the eligibility query itself, three prior rules still apply — cancelled orders are excluded (this PRD only names *refunded*), the excluded verticals list (Events, standalone Insurance, Gift Cards, Ferry) still applies, and retroactive challenge progress is granted only when the user joined inside the challenge window.
- **Multiple simultaneous challenges are the interesting shape of the query fix.** The sharpest example is an order whose *order date* falls in challenge A and whose *finish date* falls in the consecutive challenge B — it must count for **neither**, since each challenge fails it on a different rule.
