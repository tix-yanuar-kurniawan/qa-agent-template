# PLAT-60403 — Gender in profile
> **Related:** [[PLAT-60404]] · [[PLAT-60460]] · [[PLAT-60401]] · [[PLAT-60402]] · [[PLAT-60660]] · [[PLAT-60903]] · [[PLAT-59157]] · [[PLAT-57210]]

## PRD Summary

The epic body is two lines: introduce a gender field in profile, and backfill
existing users' gender from salutation. Six child stories carry the detail
(no PRD, no Confluence page, no Figma link):

- **Field** ([BE] PLAT-60404, [FE] PLAT-60460, [iOS] PLAT-60401, [Android]
  PLAT-60402 — identical AC): options are **male** and **female**; applies to
  the **main profile and the secondary profile**; **mandatory**, and leaving it
  empty triggers an **inline error message**.
- **Backfill** ([BE] PLAT-60660): map salutation to gender for existing users.
  AC: define mapping rules including unknown/other/empty cases; script is
  idempotent and auditable; rollout plan with dry-run, metrics/logging and a
  verification query/report; no unintended overwrite, "do not override
  explicitly set gender unless agreed".
- **QA** PLAT-60903 is only a placeholder ("Gender in profile").

Sprint 90; FE/iOS/Android start 2026-10-02 to 2026-10-06, so nothing is built
yet.

## Key Learnings

- **Reconciled the source.** No change log or Q&A table exists. The four
  field stories agree word for word; no description edits to compare. Two BE
  subtasks of PLAT-60404 are `Invalid` — "Update Profile Entity, DTOs & DB
  Schema" and "Integrate & Map Profile Gender with accountGender in
  tix-profile" — with no stated reason. Read as a sign the storage/mapping work
  moved or already exists; no AC is dropped because of it, but the storage
  shape is `UNKNOWN`.
- **Platform drift inside the epic.** The iOS and Android subtasks add "set
  default selection based on default salutation" (PLAT-60768, PLAT-60797) and
  call the control a "gender text field". The Responsive subtasks
  (PLAT-60824, PLAT-60825) only add the field and mandatory validation. Default
  preselection is therefore app-only; Responsive's initial
  state for a record without gender is an open question.
- **No design.** Android asked for it on 2026-09-22 and the iOS/Android
  "pending inquiry" comments (2026-09-25) point to an unreadable Slack thread
  for a PM answer. Control type, label copy and placement are `UNKNOWN`.
- **The salutation-to-gender mapping is undefined.** Both the backfill AC and
  the app default depend on it, and the AC itself lists "define mapping rules"
  as a to-do.
- **Backfill is `DEV_TESTING_ONLY` in Jira** (W/F Excp Handling) and its script
  subtasks are not started.
- **Shared form with the older profile epics.** [[PLAT-59157]] found the
  additional-profile form and Pemilik Akun share one component. Its
  inline-error pattern is save blocked, typed values kept.
- **Questions for the PM / dev:**
  1. Mapping for Mrs/Ms/Mr/unknown/other/empty salutation, and whether empty
     gender is left empty or defaulted.
  2. Does the backfill cover **secondary** profiles? "Existing users" can read
     as main profiles only.
  3. "Do not override explicitly set gender unless agreed" — was an override
     agreed? The AC default is no override.
  4. Initial Gender state on Responsive for a record without gender.
  5. Does editing salutation on the form re-derive gender?
  6. Is gender shown on the profile list/detail view, the booking traveler
     form, or the admin Care panel? Not stated anywhere.
  7. Why were the two BE schema/mapping subtasks marked `Invalid`.
