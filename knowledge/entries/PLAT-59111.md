# PLAT-59111 — [BE] Integration with Mixpanel for Experiment
> **Related:** [[PLAT-58861]] · [[PLAT-58944]] · [[PLAT-59320]] · [[PLAT-59321]] · [[PLAT-59322]] · [[PLAT-59415]] · [[PLAT-59569]] · [[PLAT-55268]] · [[PLAT-53961]] · [[PLAT-60249]] · [[PLAT-60250]]

## PRD Summary
Platform - Eiffel `[BE]` story to wire **Mixpanel Experiments** into Welcome Rewards on **TIX-MEMBER-CORE-V2**, so Grand can A/B test which **WROB campaign** a logged-in user receives when `campaignId` and `utmSource` are both blank. The Jira body is two bullets plus the attached Growth Analytic-Go library PDF; the live spec is the Confluence solutioning page finalized on [[PLAT-58944]] (v12, 2026-09-04): [Replace Amplitude Lab and Welcome Rewards Integration with Mixpanel Experiments](https://borobudur.atlassian.net/wiki/x/eIEPJQE).

Sprint 88 ships: Mixpanel Java SDK bump + `evaluateFlag` / `trackExperimentStarted` / `trackExperimentEvent`; WROB campaign resolution from the Mixpanel variant key; hybrid Redis (1-day race lock) + MySQL `mixpanel_experiment_mark` idempotency; `$experiment_started` at render when experiment-derived rewards are non-empty; `wrob_reward_claimed` on first successful experiment claim, with a claim-time safety-net exposure; fail-open on GET and fire-and-forget on claim. **Time-sensitive GV / Amplitude Lab removal is out of sprint** — subtask [[PLAT-59319]] is **Invalid**.

### Updated scope (2026-09-21)
The Jira description was updated with **Additional scope** :

1. **Device ID as anonymous identifier** ([[PLAT-60249]], Done): Member sends `deviceId` to Mixpanel, enabling experiment evaluation for **guest (non-login) users** — previously guests skipped Mixpanel entirely.
2. **Guardrail adjustment** ([[PLAT-60250]], Done): Instead of sending only `accountId + variantId`, send both `deviceId` and `accountId` as user identifiers plus the assigned `variantId`. Dedup now checks the combination of `accId & deviceId & experiment & variant` — if all four match, member does not re-send to Mixpanel.
3. **Validation rank clarification**: Explicit ordering documented:
   - WR bottomsheet: campaignId → utmSource → experiment to Mixpanel
   - WR homepage: persistent WR → campaignId → utmSource → experiment to Mixpanel
4. **Simulation scenarios** in Jira: guest→login identity merge (guest gets variant-1 via deviceId, after login gets variant-2 via deviceId+accountId), logged-in onboard flow, guest homepage flow.

## Key Learnings

### Source reconciliation
- **The Jira story is not the spec.** PLAT-59111 and its clone [[PLAT-58861]] only say "integrate with Mixpanel" and "experiment based on the attached document". The attached PDF is Grand's **analytic-go** Mixpanel library (GetVariant, manual Exposure when the user sees the feature). Implementation is **Java Mixpanel in member-core**, documented on Confluence. The Go SDK APIs (`GetAllVariants`, `GetFlagDefinitions`, `Ready`) are not part of the implementation.
- **Subtask [[PLAT-59319]] Invalid is a change log.** "Replace Amplitude Lab from GV" was scoped then marked Invalid, matching the solutioning "Later sprint (time-sensitive GV)" table. A `Dropped`/`Invalid` twin is not always a descope — here the title *and* the Confluence later-sprint table agree it is out.
- **Platform:** the story's Platforms field is **Backend**; there is no `[FE]` twin. The surfaces are the two member-core APIs (GET welcome-page, POST claim) plus homepage persist.
- **GET path is inferred.** Claim is quoted as `POST /v3/onboarding/claim`. GET is only named `welcome-page` / `OnboardingController.getWrobData`. The path `/tix-member-core-v2/v3/onboarding/welcome-page` is inferred from the sibling claim path and existing member-core prefixes — confirm on the live gateway.
- **`flag-key` and `experiment-name` are still TBD** in the YAML as of 2026-09-04.
- **Missing-identifier guard.** No events are sent only when both accountId and deviceId are missing, since deviceId alone is a valid identifier.

### Observability and open items
- **Observability is log/DB, not UI.** `$experiment_started` and `wrob_reward_claimed` are Mixpanel ingest. Idempotency is Redis keys `com.tiket.tix.members.core-mixpanel:exp:…` / `:evt:…` plus `mixpanel_experiment_mark`.
- **DeviceId source is UNKNOWN.** The Jira says "member sends device id to mxp" but doesn't specify the header name or how the backend receives it. `deviceId` is used here as a placeholder — the actual header/parameter name needs confirmation from the developer.
- **Empty first homepage render.** Problem statement #5 (empty first homepage render binds forever, exposure never fires) is still visible in the proposed "persist on first visit / no exposure from cache" flow.
