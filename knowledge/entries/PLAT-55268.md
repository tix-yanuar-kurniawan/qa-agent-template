# PLAT-55268 — Welcome Rewards on Homepage
> **Source:** Jira Epic · Confluence PRD · Figma · **Jira:** https://borobudur.atlassian.net/browse/PLAT-55268
> **Related:** [[PLAT-53961]] · [[PLAT-55792]] · [[PLAT-55793]] · [[PLAT-55867]] · [[PLAT-57823]] · [[PLAT-57688]] · [[PLAT-54052]] · [[PLAT-56907]] · [[PLAT-56702]]

## PRD Summary
**Phase II** of the same PRD that produced [[PLAT-53961]] (Phase I = dynamic missions inside the Welcome Rewards bottom sheet). Phase II adds a persistent, segmented entry point on the **Homepage** — the *New User Page* dynamic module, rendered as a section titled **"New user exclusive"** — so new users can revisit their rewards and missions after onboarding instead of getting a single one-time exposure.

The section is assembled from **modules**, which are either **mission** modules or **non-mission** modules (Points, GV, Promo Code, Banner, FTU), displayed in the fixed order Mission → Points → GV → Promocode → Banner → FTU.

Three rule sets drive it:

1. **Configuration resolution and binding.** For a user with no existing configuration, the system generates one from **Campaign ID / UTM / Default** and **persists it to that user**. Once a configuration exists, every module derives from it and **UTM / Campaign must not override it**. Guests see modules from the source configuration; after login the section is **re-evaluated against the Account ID**. A logged-in user sees the section only if at least one module is available — with none, the section must not be displayed at all.
2. **Mission module visibility.** Eligible-but-not-joined missions surface only **X days after** eligibility, and clicking marks the user **JOINED**. Joined missions show while the countdown has not ended **or** rewards remain unclaimed, and clicking opens the **Mission Detail Page**. Outside those conditions the mission is always hidden. Loyalty removes the user from a mission when eligibility expires after X days without joining, when the dynamic mission end date passes, or when the dynamic claim-rewards end time passes.
3. **Non-mission module visibility.** Driven by segmentation — **WrobSegmentNewUser** and **WrobSegmentUserWithoutTransaction** — evaluated **per module**, bound to the Account ID, with state (countdown, claim status) persisting across sessions. Expired time-sensitive modules may still render while the user stays in-segment but must be **non-interactive**; once the user **exits the segment**, every module is hidden even if still valid or unclaimed.

Two backend stories complete the epic: [[PLAT-57823]] adds the homepage welcome-reward onboarding API that must **handle an empty WR** so no empty section is rendered (with a configurable controller cache, 1 day for now), and [[PLAT-55867]] defines the **Get Mission Detail & Eligibility API** contract (mission/user status enums and the response payload).

## Key Learnings

### Source reconciliation
- **Scope is Phase II only.** The epic description points explicitly at the PRD's *(Phase II) Functional Requirements* anchor. Phase I (missions inside the bottom sheet) is [[PLAT-53961]].
- **The Jira stories are newer than the Confluence PRD.** [[PLAT-55793]] / [[PLAT-55792]] carry two clarifications the PRD body lacks: `[mission card is shown]` markers on the mission conditions, and the closing **"else, mission will always be hidden"**. The stories take precedence over the PRD wherever they differ.
- **The `[BE]` + `[FE]` mirror pair did *not* drift this time.** [[PLAT-55792]] and [[PLAT-55793]] carry byte-identical requirement tables, so the usual "only one half got the late edit" trap did not apply.
- **Two child stories are dead:** [[PLAT-56202]] `[iOS][Solutioning]` is **Dropped** and [[PLAT-55821]] `[FE][Solutioning]` is **Invalid** (superseded by [[PLAT-55793]]). So despite Phase I shipping on iOS + Android, **Phase II is web-only** (platform `Responsive`), with no iOS / Android app work. The two `Done` solutioning stories ([[PLAT-55266]], [[PLAT-55267]]) are feasibility spikes with no testable ACs.
- **Background / heading colour customization is designed but not supported.** Epic comment (Hasna Khairunnisa, 15 Jun 2026): *"background & heading/section colour customization → need to discuss, we didn't support this yet"*. The Figma nevertheless ships White and Dark background variants. Confirm before the design's dark variant is treated as in-scope.
- **`Responsive [Gajadi Ada]` — the breakpoint layouts are de-scoped in the design.** Four frames (Mobile 360 / 639, Desktop 840 / 1440) sit at 10% opacity behind that label. This *contradicts* the Jira, where [[PLAT-55793]] is platform **Responsive** and **Ready for QA**. Jira settles *whether* web is built; the design's de-scoping means no breakpoint-specific layout is specified. Worth one question to the designer about desktop layout.
- **Webview → native click-through is unsupported.** Epic comment: *"to confirm the action that user can do on the dynamic widget welcome rewards. webview click to native is not supported yet"*. Relevant if the section is ever embedded as a dynamic widget (see [[PLAT-56702]]); left as an open question.

### Undefined values
- **"X days after eligible" is never given a value** — not in the epic, the stories, or the PRD. It gates mission appearance *and* mission removal, i.e. two opposite behaviours hang off one undefined number.
- **Neither backend story names an endpoint path.** [[PLAT-57823]] ("new API welcome reward onboarding for Homepage") and [[PLAT-55867]] ("Get Mission Detail & Eligibility API") both describe behaviour without a URL, so the endpoint paths are `UNKNOWN`.
- **How `campaign_id` / `utm_source` reach responsive web is unstated.** Phase I was app-install attribution; nothing says whether web reads a URL query parameter or stored attribution. Left `UNKNOWN`.

### QA notes
- The **whitelist-timing lesson from [[PLAT-56907]] applies directly.** Logged-in users are whitelisted on *load*; guests, who do not get the screen reloaded after the login round-trip, are whitelisted on *click*.
- The core regression from [[PLAT-56907]] — clicking a mission must **never** land on a non-eligible mission page.
- **Guard vs consequence** on the expired-module rule: the expired module still renders and it is inert. A stale card is cosmetic; a *clickable* stale card is not.
- **Open contradiction on the reward nominal.** Figma comment #160 (Ernest Dimitria → Alvin Niza, Jonathan Timothy) asks whether the amount on the card is *the mission's maximum reward or the exact amount the user has at that moment*; the only reply is Alvin Niza's **"Gw kebayangnya total amount reward yg didapet"** — an assumption, not a decision, and Loyalty never answered. Meanwhile the design copy says **"Earn up to" / "Raih s.d."**, which means the opposite.
- **A second open question.** The story routes a click on *any module* to Login/Register, while the design marks **See All** as opening the Welcome Rewards pop-up. Neither source says which wins for a guest.
