## Summary
The **initial release** of the game later known publicly as **Berburu Tiket Murah (BTM)** — built internally as **Deal Dash** / **Tiket Bid & Steal**, a Deal-Dash-inspired real-time bidding game. Logged-in IDR users spend **tokens** to "steal" a predefined travel inventory (Flight, Hotel & Homes, TTD) at a **fixed discounted price**; whoever is the **last bidder when a randomized countdown expires wins** the right to buy it. Crucially it is **token-based fixed-price bidding, not a real auction** — the price never rises, so the competition is purely **timing and luck**. Released as a "Prime Project" for the Tiket Anniversary campaign: dev done 26 Jun 2025, QA 30 Jun – 18 Jul, UAT 16–21 Jul, release **29 Jul 2025**, PRD marked launched **1 Aug 2025**. Epic status **Done**, priority Medium, project **GRA (Growth and Discovery / GRAND)**, labels `DD`, `Gamification`, `Growth`, `P0-Dev-Execution`, `grand_prime`, `qa_64`, `qa_65`. 52 child issues, of which 4 ended **Invalid** and 1 was a production bug.

This is the **baseline** that [[PLAT-57190]] (Anniversary improvement), [[GRA-3099]] / [[GRA-3082]] (S66 improvements Part 1 & 2), and [[GRA-3175]] (Double Date campaign) all build on. Anything not explicitly changed by those epics still behaves as described here.

## Key Points

### Game model
- **Token-based fixed-price bidding, explicitly *not* a traditional auction.** The discounted price is a fixed amount configured per inventory (e.g. IDR 2,000,000 → IDR 200,000) and **never increases**. Winning is about *being last*, not bidding highest.
- **Winner = last bidder before the randomized countdown ends.** Ties inside the same second are broken by **system timestamp (most recent wins)**. PRD example: session ends 14:45:31 → bids at 14:44:50 ❌, 14:45:22 ❌, 14:45:31 ❌, **14:45:32 ✅ wins** (winner shown at top of page).
- **If nobody bids, the inventory stays unclaimed.**
- **Two distinct countdowns:** (a) *not-opened* state → countdown to bidding start time; (b) *active bidding* → countdown to "last bidder wins". At end: "bidding closed" state, bid input/button disabled, final price + winner shown.
- **Countdown duration is not fixed** — it is derived from a configured **total-bids → duration (seconds)** tier table, e.g. `0–100 → 1800`, `101–500 → 900`, `501–1000 → 420`, `1001–5000 → 60`, `5001–10,000 → 10`, `10,001–50,000 → 5`. More participants ⇒ dramatically shorter window.
- Bids are **locked / no retraction**; timestamp recorded. A user may bid on **multiple products simultaneously** in the same campaign, limited only by remaining tokens.

### Eligibility
- Registered tiket.com user, **logged in**, **IDR currency** (location may be anywhere as long as currency is IDR), **all platforms**, and holding at least the configured minimum **active token**.
- **Users who don't meet the criteria can still see the page but cannot play.**
- Admins can **blacklist** users for suspicious activity (initially driven via Postman / API, `GRA-925`).

### Tokens — the whole economy
| Source | Amount |
| --- | --- |
| First onboarding into the program | **10** free tokens |
| Transaction — Flight | 5 |
| Transaction — Hotel | 5 |
| Transaction — TTD | 2 |
| Transaction — other product types | 1 |
| Daily free token — **APP** (Android/iOS) | **5** per day |
| Daily free token — **WEB** (dweb/mweb) | **1** per day |
| Blibli Tiket Points conversion | **1,000 pts → 1 token**, later changed to **500 pts → 1 token** |
| Share to a friend | +1 token |

- **Daily tokens expire at end of day and renew the next day, GMT+7** — called out as needing to be in the T&C.
- The **platform split (APP 5 vs WEB 1)** is evaluated by the platform the user is on **when they first open the landing page that day** — a deliberate lever to push app downloads.
- **Share and Earn:** the sharer gets +1 token once the **recipient clicks the link and lands on the landing page in a logged-in state**; the sharer then receives a push notification (`GRA-2096`, refined in [[GRA-3099]] / `GRA-2864`). Share UTMs: `utm_source=whatsapp|facebook|twitter|copy_link`, `utm_medium=others_product_share_berburu_tiket_murah`, `utm_campaign=tiket_anniversary_berburu_tiket_murah`.
- **Blibli Tiket Points conversion rate was halved from 1,000 → 500 points per token** by a late managerial request (`GRA-2843` FE / `GRA-2848` BE), which also had to be reflected in the T&C doc and the "How to play" page module.
- Loyalty point-deduction **remark changed from `game-dealdash` to `game-btm`** ([[GRA-3099]] / `GRA-2864`; see Confluence *Loyalty x Growth Point Deduction Deal Dash*, page 3551821845).
- Admins can **inject tokens** from the dashboard.

### Consent & identity masking
- On onboarding the user must **consent that their identity is disclosed to other players**, shown as either:
  - **First name + 1-character last name** — `Novita O.` (first name only if there is no last name — `Novita`), **or**
  - **masked email**, by local-part length:
    - **> 4 chars** → show first 3, mask the rest: `novi08111@gmail.com` → `nov***@gmail.com`
    - **= 4 chars** → show first 2, mask 2: `joko@gmail.com` → `jo**@gmail.com`
    - **≤ 3 chars** → show first char only: `ari@` → `a**@`, `li@` → `l*@`, `zo@` → `z*@`
- The user must also **tick a consent box** agreeing to claim the product within X days of the announcement.

### Live/social signals
- The page shows **current users *viewing* the bidding in real time** (a FOMO device). **"Total users who viewed" was explicitly rejected** as out of scope. Backed by a **heartbeat endpoint** (`GRA-2232`).
- **"X users are bidding this item"** = total **unique** users who bid on that inventory.
- Two bid-history surfaces:
  - **`#HISTORYINVENTORYPAGE`** — same for everyone: last **10** bidders with name + timestamp (mini PDP shows **3**, expandable to 10).
  - **`#PERSONALINVENTORYPAGE`** — per-user history of their own bids across products, with tokens spent and won/lost outcome.

### Winning and redemption
- Winner notified via **Email + WhatsApp + push notification/inbox**; **losers** notified via **Email + PN/inbox** after the countdown ends. Masked winner info is displayed publicly.
- PN/inbox trigger set: **Bid Available, Bid Placed, Bid Stolen, Bid Lost, Bid Won, Blacklisted, Blacklist Lifted** (Bid Won also Email + WA with SMS failover).
- The prize is a **promo code / Gift Voucher locked to the exact inventory won** — same hotel *and* room type, same route *and* airline, same TTD package. Booking/travel was **locked until 31 December 2025**.
- **Quantity cap per win:** 1 night and 1 room for hotel, 1 passenger for flight, 1 visitor for TTD.
- **Purchase window after winning was raised from 2 hours to 6 hours** (`GRA-2843`) — this cascaded into the **T&C (ID + EN)**, the **post-win bottom sheet**, and the **How to play** page. The admin dashboard also has a configurable "time window to complete purchase after bidding end" (PRD example: 7 days).
- **Penalty:** winning but failing to pay in time results in penalisation (suspension from bidding / blacklist), which is why the consent tick exists.
- Chosen tech route was **Promo-team GV/promo-code issuance** (`GRA-903`) rather than the heavier Kuber/vertical price-injection option; a tag/rule must mark the discount as expired once used once or once the window lapses, to stop repeat discounted purchases.

### Admin dashboard configuration (`GRA-857`, `GRA-858`, `GRA-925`)
Per-inventory: Product ID (auto-pulls image, with manual image upload fallback); Hotel → inventory public ID / country / hotel name / room ID; Flight → `originCity`, `destinationCity`, `originAirport`, `destinationAirport`, `airline`, seat class; TTD → itemId / country / name / package ID / vendor ID. Plus **original price**, **fixed discounted bid price**, **inventory open time**, **inventory end time**, **bidding start time**, the **countdown duration tier table**, **maximum bid limit per user per product (`-1` = unlimited)**, **purchase-completion window**, **token injection**, and **user blacklisting**.

### Out of scope in the initial release
- **Gift Vouchers are not sold as biddable products** (only real inventory) — note this reversed later: [[PLAT-57190]] *buys* GV value packs as a **token source**, which is not the same thing as bidding on a GV.
- **"Total users viewed"** metric rejected in favour of live concurrent viewers.
- **Differentiating bidding for new vs existing users** was ruled out by the Growth tech team.
- "If user has no tokens, show a prompt on how to earn more" was struck from Phase 1.

### Domain risk notes
- **The tokens are the risk surface, not the bidding UI.** Four token sources (onboarding, transaction, daily, points conversion, plus share) with different lifetimes — daily tokens expire nightly at GMT+7 while the others persist — so almost every token bug is a *mixed-balance* bug.
- **Two numbers are easy to get wrong and both changed late:** points→token is **500** (not the PRD's original 1,000) and the post-win purchase window is **6 hours** (not 2).
- **The countdown tier table means load changes behaviour.** With 5 concurrent bidders the window is 1,800 s; at 10,001 bidders it is 5 s.
- **`-1` means unlimited** for max bid limit per user per product — a sentinel value.
- **Re-shared links are a proven defect area** (`GRA-3074`).
- **Platform matters for tokens and for autoplay.** Daily tokens differ APP (5) vs WEB (1), and audio autoplay works only on iOS ([[GRA-3099]]).
