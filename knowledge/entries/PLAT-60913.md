# PLAT-60913 — [FE] Development for Supporting Corporate Multi-Entity
> **Related:** [[PLAT-57795]] · [[PLAT-61000]] · [[PLAT-61001]] · [[PLAT-61522]] · [[PLAT-61573]] · [[PLAT-58696]] · [[PLAT-58702]] · [[PLAT-58703]] · [[CRP-6807]] · [[CRP-7032]] · [[CRP-7023]]

## PRD Summary

This is the member FE (tiket.com web, `Responsive`) slice of Corporate Multi-Entities 2.0. It is the FE twin of [[PLAT-57795]], which covered the Member BE contracts. It has two subtasks:

- **[[PLAT-61001]] — redirect.** The FE stops deciding post-login destination from `b2bcorpRole`/`accessRoleName` and instead navigates to `loginRedirection` from the login exchange response. A `&ref=` on the login URL still wins. The PM confirmed this in the Slack thread linked from the Endpoint Change Spec. `accessRoleName` was removed from the login body.
- **[[PLAT-61000]] — switch refresh.** When the user switches billing entity or traveller on tiket.com (booking-center → `PUT /tix-corporate/booking-center/auth/sync`), or switches dashboard on the Corporate Dashboard (`PATCH /tix-corporate/corporate-dashboard/multi-entity/sessions`), the FE refreshes session state. The booking flow then runs on the selected entity, with no re-login. Corporate forwards both triggers to the Member sync proxy, which replaces `b2bCorporateData` and deactivates the account's other sessions.

Sources: Jira story + 4 subtasks; master PRD *2026-04-26 Corporate Multi-Entities 2.0* (v49, 2026-09-30); *[MEMBER] Account Improvement* (v14); *Endpoint Change Spec* (v9, 2026-08-20); *[WIP] Multi Entities Phase 2* (v87); *Vertical Related* (v33, 2026-10-21).

## Key Learnings

- **Two rules in the PRD conflict on the active entity after login.** §7 *Eligible switching entity* #1 and the Member spec say login sets `corporateId == homeCorporateId`. The §5.2 activity diagram and §7 #10 say a direct tiket.com entry defaults the billing entity to the **last-used** one. Login resetting the session to home is the documented Member behaviour; the selector pre-fill is `UNKNOWN`. Raise this with Mayfa.
- **ACCOUNT-level session data makes re-login a cross-device write.** `b2bCorporateData` is stored at `SharedLevel.ACCOUNT`. A switch on device 1 deactivates device 2 ([[PLAT-58702]]). If device 2 then logs in again, login rewrites the account-level blob to the home entity. Device 1 is still active and was on entity B, so its context may silently flip back to A. No source says whether that is intended.
- **`ref` priority is the only documented redirect rule besides `loginRedirection`.** No source covers ref validation, such as an external-domain `ref` (an open-redirect risk). Nothing defines a fallback when a corporate user's `loginRedirection` is empty. The destination is an open question.
- **OTA roles are explicitly deferred.** *[WIP] Multi Entities Phase 2* lists `agent_owner`/`agent_admin` → corporate dashboard and `agent_booker` → tiket home page, but marks it "wait until OTA release first".
- **The selector UI belongs to Corporate FE, not this story.** The booking-center widget and pages come from Corporate (`GET /tix-corporate/booking-center` via disco, with the URL "provided by corp FE"). So do the field-visibility rules in PRD §7 #3 (Billing Entity hidden for single-entity users, Traveller disabled without centralized booking). Those rules are CRP scope. What this FE owns: the context switch lands, persists and drives the booking flow.
- **Context refresh is observable via `GET /tix-corporate/booking-center/session`.** Gateway headers can't be seen from the FE ([[PLAT-57795]] hit the same wall). That endpoint returns the current assigned `corporateID`, and `GET /booking-center/travelers?corporateID=` marks the selected traveller. The Corporate Booking Form's disabled, pre-filled billing-entity field (PRD §5.2) is the UI signal.
- **Jira text is still stale.** The story still says `chargedCorporateId` / `chargedEntityId`. The live names are `corporateID` (assigned) + `originalCorporateID` (home) + `parentCorporateID`, as in [[PLAT-57795]].
