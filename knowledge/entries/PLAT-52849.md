# PLAT-52849 — [BE] Cron Point Activation – Per-User Cache Check & Retry
> **Type:** Story · **Status:** Done · **Priority:** Medium · **Parent:** [[PLAT-52850]]
> **Related:** [[PLAT-52850]]
> **Jira:** https://borobudur.atlassian.net/browse/PLAT-52849

## Summary

When a cron job activates pending points and PNV status was preloaded into cache during the initial process, the subprocess for a single user must re-read PNV status from cache instead of using stale PNV data passed via RabbitMQ. If PNV retrieval fails, it should retry using existing retry mechanisms. Retry must be user-scoped rather than batch-scoped, and failures should be logged.

## Key Points

- Subprocess re-reads PNV status from cache per user during point activation, not stale PNV from RabbitMQ payload.
- If PNV retrieval fails, retry using existing retry mechanisms.
- Retry must be user-scoped, not batch-scoped.
- Passing PNV via RabbitMQ payload should be deprecated.
- Failure should be logged.

## Details
**GIVEN**
A cron job activates pending points
And PNV status was preloaded into cache during the initial process

**WHEN**
The subprocess processes point activation for a single user

**THEN**
The subprocess re-reads PNV status from cache for that user
If PNV retrieval fails, retry using existing retry mechanisms
Instead of using stale PNV data passed via RabbitMQ

**Additional Details**

* Retry must be user-scoped, not batch-scoped
* Current behavior of passing PNV via RabbitMQ payload should be deprecated
* Failure should be logged
